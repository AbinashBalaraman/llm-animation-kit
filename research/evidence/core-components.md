# Core components evidence memo

Research date: **12 October 2026**. Scope: renderer, animation assets, interchange, lip sync, and assembly. **No component was installed, executed, benchmarked, or experimentally tested.** D = official documentation inspected; C = selected source code inspected; I = design inference. Source inspection is narrower than a code audit. Links to `main` are moving references; implementation must pin releases and hashes. Compute and integration assessments are I unless explicitly attributed.

## Recommendation

Use a validated scene/action document compiled into **Blender + Rigify**, retain editable `.blend` assets, render shots to image sequences, and assemble with **FFmpeg**. Use **Rhubarb** for a first pass at mouth timing with editable overrides. Curate **Poly Haven/ambientCG** environment assets. Build a small original, redistributable action library; allow user imports without bundling restricted assets. Keep glTF as an exchange/preview derivative. Remotion, Motion Canvas, and Manim solve useful neighboring problems but should not be mandatory dependencies of the character-animation core. This is a proposal, not a measured superiority claim.

## Operational decisions and caveats

**Version/hardware baseline.** Blender's [requirements](https://www.blender.org/download/requirements/) list a four-core SSE4.2 CPU, 8 GB RAM and 2 GB GPU memory as minimum for its relevant desktop table, with eight cores, 32 GB RAM and 8 GB GPU memory recommended. These are application requirements, not evidence that our target scenes render acceptably. Provisionally target 32 GB RAM and a compatible 8–12 GB GPU for development; measure a representative 1080p shot before promising throughput. The latter is our planning assumption. Prefer EEVEE for the initial stylized pipeline, with Cycles available per shot; this is a workflow choice, not a measured speed claim.

Use 5.2.2 LTS as the first candidate, subject to checking chosen assets/add-ons. [4.5 LTS remains supported through July 2027; 4.2 is end-of-life](https://www.blender.org/download/lts/4-2/). Keep a project on one tested version. Blender's [compatibility notes](https://developer.blender.org/docs/release_notes/compatibility/) document 5.2 Geometry Nodes RNA-path changes: accepting random asset versions is not a compatibility strategy.

**Authoring versus delivery.** Core glTF animation targets transforms and morph weights; the spec explicitly does not represent nonlinear time input directly. Blender's exporter documentation says animation support covers object transforms, pose bones and shape-key values; other animated properties can be ignored. Bake evaluated motion for delivery, but retain authored actions, rig controls, constraints and material graphs in `.blend`. Keep semantic IDs, joint maps, viseme maps, contact anchors and clip tags in a versioned sidecar. Do not promise pixel-identical glTF/browser and Blender renders.

**Rig and motion strategy.** Start with one approved humanoid topology/rig family and semantic controls, not arbitrary uploaded meshes. Preserve the metarig for regeneration; [Rigify usage](https://docs.blender.org/manual/en/latest/addons/rigging/rigify/basics.html?highlight=pose+mode) documents matching bones and retaining regeneration capability. Author/licence a small set of walk, stop, turn, sit, reach, grasp, release, nod and reaction clips with root displacement and contact metadata. Compose clips, then solve contact and gaze constraints. Retargeting is a repairable import step, not proof that every clip works on every body. CloudRig was not deeply audited; no need to adopt both frameworks initially.

**Audio/assembly.** Render independent numbered image sequences with explicit frame count, rational frame rate and color metadata; preserve voice/effects/music stems. FFmpeg's documented sequence input and concat/filter tools provide the assembly surface. Normalize loudness as a separate, configurable finishing pass; validate duration, missing frames, audio start/end, and clipping. A job should retain logs, exact command arguments, binary version/configuration, input hashes and output manifests. Encoder choice must be tied to the actual distributed build's license, including optional libraries.

**Lip sync.** Use dialogue audio before final shot timing. Rhubarb supports a transcript hint and machine-readable cues; map these to approved mouth shapes with manual correction and separate emotion/blink/gaze tracks. Do not advertise multilingual parity or realistic facial acting from this tool. Test the selected voice, language and performance style before committing to it. A public [maintainer statement](https://github.com/DanielSWolf/rhubarb-lip-sync/issues/95) says Rhubarb is not designed for real-time applications, which is acceptable for offline generation.

**Asset rights and service terms.** Poly Haven's July 2026 API page now allows commercial live API use for free, requiring clear source credit and a unique User-Agent; older posts requiring commercial permission are superseded by that page. Those API conditions are distinct from CC0 asset rights. Keep a per-asset manifest of source URL, author if known, license, retrieval date, hashes and permitted redistribution. The Adobe-hosted Mixamo FAQ forbids raw-character/animation-file distribution; its posting is older, so reconfirm current terms before any expanded use. Build the bundled motion library from commissioned/original work with explicit redistribution rights rather than assuming downloaded motion is open-source.

**Evidence limits.** Official documentation establishes exposed capabilities and stated terms; inspected examples establish plausible programmatic entry points. Neither proves unattended reliability, reference-video quality, hardware throughput, asset compatibility, or legal sufficiency of a proposed packaged distribution. Those remain implementation validation tasks.
